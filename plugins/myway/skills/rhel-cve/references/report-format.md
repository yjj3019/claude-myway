# Confluence용 RHEL CVE 리포트 형식

CVE 한 건·여러 건 또는 RHSB를 한 파일로 작성한다. CVE 한 건은 `CVE-YYYY-NNNNN_리포트.md`, 여러 건이나 RHSB는 `RHEL_CVE_리포트_YYYYMMDD.md`로 저장한다. 파일 구조를 `scripts/check_report.py`로 검사하고, 사실·출처는 원문과 별도로 대조한다. 구조 검사 통과는 사실 확인이 아니다.

## 구조

아래 제목과 순서를 지킨다. `Environment`, 패키지 표 제목, `참고문서`는 Setext 제목이다. `### 1`부터 `### 5`까지 외의 임의 섹션은 추가하지 않는다.

```markdown
# {CVE-ID 나열} - {취약점 한 문장 설명} ({RHSB 번호, 확인된 경우})

보안등급

Impact : {Critical/Important/Moderate/Low 또는 미확인}
CVSS v3 Base Score : {점수 또는 미확인} (Red Hat 기준)

기준일 : {YYYY-MM-DD} (확인한 자료와 갱신일)

Environment
-----------

* Red Hat Enterprise Linux {N}

### 1. 취약점 개요
* **분석 대상 제품** (버전별 해당 여부와 스트림)
* 취약점의 성격과 공격 조건; 다건이면 CVE별 설명

### 2. 영향
* 악용 결과, 공격 조건, 기본 구성과 영향 없는 조건

### 3. 완화 방법(Mitigation)
* 패치 전 임시 조치와 부작용. 확인된 확인·적용·검증·원복 명령은 코드 블록으로 제시
* 완전한 해결은 패치뿐입니다.

### 4. 추가 정보
* 실제 조회한 Bugzilla·CWE와 확인된 패치 점검 명령, 백포트, 미패치 스트림과 조사 한계

### 5. 결론
* 우선순위, 권고, 출처가 확인된 악용 정황과 미패치 스트림을 가능하면 3문장 이내로 정리

영향을 받는 패키지 및 발행된 레드햇 보안 공지 ( {YYYY-MM-DD} 기준 )
------------------------------------------

{대상 CVE와 신규·변경 행 표시 규칙}

| RHEL | Lifecycle | Components | Fixed Package | RHSA | Release Date | 비고 |
| --- | --- | --- | --- | --- | --- | --- |

명시적으로 영향을 받지 않는다고 언급되지 않은 한, 이 목록에 있는 제품의 모든 마이너 업데이트 스트림에 포함된 기존 패키지 버전은 모두 취약한 것으로 간주해야 하며, 전체 분석이 이루어지지 않았을 수도 있습니다.

참고문서
----

* 실제 조회한 RHSB, CVE, RHSA, Bugzilla, 업스트림·타 기관 자료
```

## 작성 및 검증

- 제목의 여러 CVE ID는 쉼표로 구분한다. 패키지 표 제목에는 실제 기준일을 `YYYY-MM-DD`로 넣는다. 이전 형식의 `YY/MM/DD`도 검사기는 허용한다.
- 별도의 내부 보고서 참조는 기본적으로 포함하지 않는다. 사용자가 명시적으로 요청하고 관련 자료의 존재와 대상 CVE를 확인한 경우에만 포함한다.
- Red Hat 영향도와 CVSS는 원문에서 확인한 값만 쓴다. 기관별 점수가 다르면 출처와 차이를 병기한다. 미확인은 이유와 함께 표시한다.
- `Environment`의 RHEL 메이저 판정은 Hydra `product_name`의 정확히 일치하는 행을 근거로 한다. EUS·E4S·ELS 등은 별도 스트림으로 표시한다. Statement만으로 영향을 판정하지 않는다.
- 패키지 표는 7개 컬럼을 유지한다. `package_state`와 `affected_release`를 구분하고 패치 미발행·미확인 스트림도 누락하지 않는다. 수정 패키지는 확인된 NVR과 아키텍처를 쓰고 epoch는 제거한다. 모듈 ID만 확인된 경우 비고에 모듈 스트림 버전임을 표시한다.
- 표 아래 고정 문구는 제공된 형식의 일반 주의문이며 각 제품·스트림이 실제로 취약하다는 독립 근거가 아니다. 확인된 제품별 상태와 분석 범위를 본문과 표에 명확히 구분한다.
- fix_state는 Affected, Fix deferred, Out of support scope, Not affected, Will not fix, Under investigation을 구분한다. 지원 범위 밖은 영향 없음이 아니다. JSON/XML 충돌은 양쪽 값과 채택 근거를 밝힌다.
- RHSA가 20개를 초과하면 각 메이저 기본 스트림을 우선 확인하고 축소 범위·미확인 행을 명시한다. kpatch와 일반 패치, EUS/E4S/AUS 및 ELS를 구분한다.
- 완화 조치의 확인·적용·검증·원복 명령과 부작용은 실제로 확인한 내용만 적는다. 확인하지 못한 명령은 만들지 않는다. 패치가 유일한 해결책이라고 단정할 근거가 없으면 미확인 사유를 적는다.
- 악용 사실은 출처를 명시하며 Red Hat 공지에 없는 정보는 구분한다. EPSS·KEV를 사용하면 확인 시점과 근거를 4장 또는 5장에 적는다. 로그인 장벽이나 자료 접근 실패, 범위 축소, 대체 소스는 4장에 기록한다.
- 참고문서는 실제로 조회한 URL만 포함한다. 점수·NVR·RHSA·발행일을 원문과 수동 대조한다. 한국어 합니다체를 사용하고 HTML·색상 배지·이모지를 넣지 않는다.
- 전달 메시지는 산출물 경로와 미확인·판단 필요 항목을 간결하게 적는다. 실제 외부 시스템 게시나 전송은 사용자의 요청에 따른다.
