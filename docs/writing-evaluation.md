# writing 변경 비교 평가

`writing` 지침 변경이나 외부 교정 스킬의 도입을 판단할 때 쓰는 수동 절차다. 이 문서는 일반 글쓰기 때 읽는 스킬 지침이 아니다. 기존 `scripts/run_tests.py`는 저장소 검증기의 동작을 검사하며 모델의 글쓰기 품질을 평가하지 않는다.

## 1. 비교 준비

1. 비교할 기준본과 변경본의 파일·버전·커밋 또는 작업본 변경 내용을 기록한다. 사용자가 공유를 허락한 자료 또는 아래 가상 입력만 사용한다. 비밀·실제 개인 정보는 기록하지 않는다.
2. 같은 입력, 사용자 요청, 모델, 설정과 도구 접근 조건에서 각각 독립적인 새 대화로 결과를 만든다. 비용이나 사용 가능한 환경은 사전에 확인한다. 서로 다른 모델을 사용했다면 스킬 차이와 모델 차이를 구분할 수 없다고 기록한다.
3. 후보에게는 입력과 통상적인 사용자 요청만 전달한다. 이 문서의 기대 조건, 평가표, 다른 후보의 출력과 평가 의도는 전달하지 않는다. 스킬이 이미 동일 사례를 예시로 포함하면 그 노출을 기록하고 별도의 미노출 입력도 사용한다.
4. 출력 원문을 바꾸지 않고 중립 라벨 A·B로 바꾼다. 라벨과 후보의 대응표는 평가자에게 숨긴다. 평가자가 이전에 결과나 후보를 알고 있다면 무엇이 보였는지 밝히고 블라인드 평가라고 부르지 않는다.

## 2. 가상 입력과 보호 조건

실제 실행 시 각 행의 입력·요청만 후보에 제공한다. 보호 조건은 평가자에게만 제공한다. 이 사례들은 반복 시험을 위한 최소 기준이며 실제 글의 품질을 대표하지 않는다.

| 사례 | 입력과 요청 | 보호 조건 |
|---|---|---|
| 범위 제한 | `실험 환경에서 3회중 2회 성공했습니다. 운영 환경에서는 확인하지 않았습니다.` 오탈자·띄어쓰기만 교정한다. | 횟수·실험 환경·운영 미확인을 유지한다. 표현과 문장 순서를 임의로 바꾸지 않는다. `3회 중`과 `3 회 중`은 모두 허용한다. |
| 개인 말투 | `자, 연결은 두 번 실패했네요. 원인은 아직 모르겠습니다.` 개인 말투를 유지하며 다듬는다. | 두 번 실패·원인 미상·제공된 말투를 유지하고 새 감정·경험을 만들지 않는다. |
| 기술 조건 | `설정 A가 켜진 경우에만 결과가 Affected일 수 있습니다. Not affected는 별개입니다.` 의미와 기술 문자열을 유지하며 다듬는다. | 조건·가능성·두 상태명을 보존하고 검증 결과나 인과를 새로 만들지 않는다. |
| 공식 사실 | `공식 자료에 따르면 기능 A는 기본적으로 비활성화되어 있습니다. 성능 영향은 확인되지 않았습니다.` 이 두 문장만 포털 글에 맞게 다듬는다. | 출처 귀속·기본 비활성화·성능 미확인을 보존한다. 근거 없는 수치를 넣거나 제목·메타를 추가하지 않는다. |

## 3. 판정과 기록

- 같은 평가자가 입력과 두 출력을 같은 기준으로 본다. 우선 사실·수치·부정·조건·출처와 기술 문자열을 비교하고, 원문에 없는 경험이나 감정이 추가됐는지 확인한다. 요약 요청이면 결론과 적용 범위를 바꾸지 않는 생략은 허용한다.
- 의미 보존을 통과한 결과끼리만 요청 범위, 어색한 수정, 말투와 가독성을 비교한다. 고유 문체나 정확한 용어의 반복을 자동으로 감점하지 않는다. 수정이 필요 없는 원문을 유지하는 것도 적절한 결과다.
- 판단마다 입력과 출력의 해당 표현을 근거로 남긴다. 국어 규범의 허용 여부가 불확실하면 공식 근거를 확인하거나 미확인으로 기록한다. 확신도나 숫자 점수만으로 우열을 만들지 않는다.
- 평가 후에만 대응표를 공개하고, 날짜·기준본·변경본·모델·설정·실행 횟수·가린 범위·실패 또는 미실행 항목을 기록한다. 모델의 자동 선택 또는 반복 실행이 확인되지 않았다면 그렇게 쓴다.
- 한 번의 소수 사례는 탐색 결과로 취급한다. 일반적 성능이나 오류율을 주장하려면 추가적인 미노출 사례와 반복 실행이 필요하다. 서로 다른 평가자의 검토는 가능하면 사용하되 필수 유료 도구나 특정 모델을 요구하지 않는다.

## 4. 절차 시험 기록 (2026-10-27)

기준본은 1.4.1 공개 커밋 `cc9320529e2b58a7b2faaa40a7a233fcce94fa93`, 변경본은 1.4.2 로컬 작업본이다. 두 독립 대화에서 writing과 필요한 참조 파일을 수동으로 읽고 같은 가상 원고와 요청에 각각 한 번 답했다. 기준본은 GitHub 연결, 변경본은 로컬 파일에서 읽어 자료 접근 경로가 달랐다. 두 대화는 같은 세션 모델을 상속했고 세부 생성 설정은 기록하지 않았다. 자동 스킬 검색·호출 여부는 시험하지 않았다.

입력: `어제 기능 A를 켰습니다. 테스트 환경에서 연결을 세 번 시도했고 두 번 실패했습니다. 원인은 아직 모르겠습니다.` 개인 블로그용으로 다듬고 태그 2개를 제안하되 사실·감정은 추가하지 않도록 요청했다.

- **A — 변경본:** `어제 기능 A를 켰습니다. 테스트 환경에서 연결을 세 번 시도했는데, 두 번 실패했습니다. 원인은 아직 모르겠습니다.` 태그: `#기능A #테스트기록`.
- **B — 기준본:** `어제 기능 A를 켰습니다. 테스트 환경에서 세 번 연결을 시도했는데, 그중 두 번 실패했습니다. 원인은 아직 모르겠습니다.` 태그: `#기능A #연결테스트`.

작성자와 후보명을 가린 A·B 및 원문·동일 기준을 독립 평가자에게 제공한 결과, 둘 다 사실·횟수·불확실성을 보존하고 태그를 요청대로 제안해 우열을 정할 근거가 부족하다고 판정했다. 대응표는 판정 후 여기에 공개했다. 작성자와 통합자는 대응을 알고 있었고, 출력의 문장 차이는 평가자에게 보였다. 가상 원고 1건의 각 1회 실행이므로 품질 향상이나 재현성을 입증하지 않는다.

## 5. 네 사례 비교 (2026-10-27)

위 2절의 네 가상 입력을 기준본 1.4.1과 변경본 1.4.2에 각각 한 번씩 제시했다. 각 후보는 독립 대화에서 네 요청을 함께 처리했고, 해당 스킬과 참조 파일을 수동으로 읽었다. 기준본은 고정 GitHub 커밋 `cc9320529e2b58a7b2faaa40a7a233fcce94fa93`, 변경본은 로컬 작업본이다. 두 대화는 같은 세션 모델을 상속했으나 세부 생성 설정은 기록하지 않았고, 기준본과 변경본의 파일 접근 경로도 달랐다. 자동 스킬 호출은 시험하지 않았다.

두 후보의 네 출력은 모두 같았다.

1. `실험 환경에서 3회 중 2회 성공했습니다. 운영 환경에서는 확인하지 않았습니다.`
2. `자, 연결은 두 번 실패했네요. 원인은 아직 모르겠습니다.`
3. `설정 A가 켜진 경우에만 결과가 Affected일 수 있습니다. Not affected는 별개입니다.`
4. `공식 자료에 따르면 기능 A는 기본적으로 비활성화되어 있습니다. 성능 영향은 확인되지 않았습니다.`

후보명·작성자·모델을 가리고 두 출력과 입력을 같은 평가자에게 제시했다. 평가자는 출력이 네 사례 모두 동일하며 수치·미확인·개인 말투·조건·상태명과 두 문장 요청을 유지했다고 판정했다. 판정 후 공개한 대응은 A가 기준본, B가 변경본이다. 통합자는 대응을 알고 있었다.

사례마다 별도 대화를 열지 않아 앞 사례가 뒤 사례에 영향을 줄 수 있다. 스킬에 비슷한 예시가 있어 입력이 완전히 미노출됐다고 보장하지 못한다. 각 사례는 한 번만 실행했으므로 다른 입력이나 반복 실행의 결과, 일반적인 품질 향상 또는 오류율은 판단할 수 없다.
