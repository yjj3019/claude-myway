# 사실, 경험, 개인정보 기준

문체보다 우선한다.

## 사실과 경험의 경계

- 작성자가 제공한 사실, 직접 경험, 개인 의견, 외부 자료의 설명을 구분한다.
- 구매, 설치, 방문, 테스트, 측정, 만족, 실망, 비용, 미래 계획을 지어내지 않는다.
- "직접 써 보니", "계산해 보니", "구성해 보니"는 해당 경험이나 결과가 제공된 경우에만 쓴다.
- 외부 자료를 읽은 사실을 사용 경험처럼 쓰지 않는다.
- 분석 주제·비교 제품과 실제 사건의 대상을 구분한다. 연결이 명시되지 않은 제품을 장애 서비스나 원인으로 단정하지 않는다. 제목도 같은 기준을 따른다.
- 도입에 만든 질문을 실제 고객이나 현장 발언처럼 꾸미지 않는다. 실제 발언이 아니면 인용 부호 없이 독자의 질문으로 쓴다.
- 장점과 함께 확인된 한계나 적용 조건을 쓴다. 균형을 맞추려고 단점을 만들지 않는다.
- 비용, 버전, 날짜, 설정값, 측정값은 관련 있고 근거가 있을 때만 넣는다. 예시 수치는 실제 측정과 구분하고 계산에는 조건을 붙인다.
- 최신 정보는 가능하면 공식 자료로 확인하고 기준 날짜를 적는다. 확인하지 못한 내용은 단정하지 않는다.
- "전문가들은", "업계에서는"처럼 출처 없는 권위로 주장을 보강하지 않는다. 시간 순서나 동시 발생을 인과관계로 바꾸지 않는다.
- 불확실성 표시는 정확성의 일부다. "가능성이 있다", "확정하기 어렵다", "제공된 로그 기준"은 필요한 곳에 남긴다.

## 개인정보와 비밀정보

- 본문, 예시, 작성 메모, 보존 확인표 어디에도 넣지 않는다.
- 토큰·비밀번호·키는 삭제하거나 `<마스킹>`으로 바꾼다.
- 계정명·호스트명·내부 주소·고객사명은 `user-a`, `node-a`, `<내부 주소>`, `고객사 A`처럼 일관되게 치환한다.
- 분석에 필요한 오류 코드·시간 간격·버전·수치는 유지한다. 익명화했다는 사실은 필요할 때 한 줄로 표시한다.
- 원문 보존과 충돌하면 식별정보만 치환하고 사실은 유지한다.

## 기술 글 추가 기준

- 제품명과 기술 용어는 정확한 표기를 유지한다. 처음 한 번 필요한 만큼 풀어 준다.
- 문장만 다듬는 요청에서는 코드 블록, 인라인 코드, 명령 옵션, 경로, 설정 키와 값, 링크 대상, 메타데이터를 보존한다. 익명화와 명시적으로 요청받은 기술 수정은 예외다. 오류가 의심되면 임의로 고치지 말고 확인 사항으로 분리한다.
- 명령어는 언어를 표시한 복사 가능한 코드 블록으로 쓴다. 명령과 출력을 구분하고 실행 위치·권한·환경·치환값은 확인된 범위에서 설명한다.
- 단계형 안내는 선행 조건 → 실행 → 결과 확인 순서로 쓴다. 실행하지 않은 결과를 검증됐다고 쓰지 않는다.
- 성공·실패 표시는 실제 확인한 결과에만 붙인다.
- 공식 발표, 제공 예정 일정, 현재 이용 가능 여부를 구분한다. "기능이 있다"와 "우리 환경에서 검증됐다"를 구분한다.
- 링크에는 자료명이나 목적을 쓴다. 출처는 뒷받침하는 주장 가까이에 둔다.
- 이미지를 쓸 때는 무엇을 보여 주는지 짧게 설명하고 의미 있는 대체 텍스트를 붙인다.
- 기존 문서를 갱신할 때는 관련 설정·예시·링크도 함께 확인한다. 과거 기록은 당시 기준임을 표시한다.
- 효과를 과장하지 않는다. 도움이 되는 조건과 별도로 확인할 항목을 밝힌다.
- 문서·가이드는 한 문장에 핵심 정보를 담고 행동 주체와 적용 조건을 명확히 쓴다.
